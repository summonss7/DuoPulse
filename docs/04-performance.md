# 04 · Стратегия скорости

«Работало очень быстро» — требование №1 из карточки. Скорость трактуется как три
измеримых вещи: **быстрый запуск**, **отзывчивый интерфейс**, **быстрая загрузка
страниц и видео**. Ниже — что делаем и как это измеряем.

## 1. Четыре рычага

### 1.1 Лёгкая оболочка

- Tauri 2: нативное окно + системный WebView2 (Chromium). Нет собственного
  bundled-браузера → дистрибутив ~10–20 МБ, старт не читает сотни МБ с диска.
- UI браузера (хром) — Svelte-бандл < 300 КБ gzip, рендерится локально, без сети.

### 1.2 Меньше грузить: блокировщик

Главная статья «медленного YouTube» — реклама и трекеры. Фильтрация на уровне
Core **до** загрузки ресурса (Rust, `adblock-rs`, списки EasyList + uBO-синтаксис):

- запросы режутся в сетевом обработчике WebView2 → экономия трафика и CPU;
- косметическая фильтрация (скрытие рекламных DOM-узлов) — инжектируемым скриптом;
- скриптлеты `##+js(...)` (карточка duopulse-043): JS-функции uBO (set-constant,
  aopr, json-prune, …) исполняются в контексте страницы — срезают anti-adblock
  и конфигурацию рекламы (YouTube-преролл) до того, как её увидит плеер; набор
  генерируется из @adguard/scriptlets и вкомпилирован в бинарник;
- white-list per-site (кнопка в адресной строке) — блокировщик никогда не «ломает»
  сайт без ведома пользователя.

Ожидаемый эффект (по данным движка Brave/uBO): −30–60% сетевых запросов на типичной
странице, YouTube — без рекламных пауз и «пропустить рекламь» вообще.

### 1.3 Не работать, когда не просят

- **Спящие вкладки**: вкладка неактивна N минут (по умолчанию 5) → приостановка
  энергоэффективным режимом WebView2 (TrySuspend: JS/таймеры/воркеры заморожены,
  состояние страницы сохранено; реализовано — задача 2.3); пробуждение по клику.
  Исключения: вкладки со звуком/активным видео, режим «закрепить».
- **Отложенная активация**: восстановление сессии открывает вкладки лениво
  (заголовок/фавикон из кэша, контент — при первом переключении).
- **Новая вкладка — мгновенно**: статический локальный HTML (без fetch), поиск
  стартует с первого символа из локального индекса.

### 1.4 Быстрые пути данных

- Тёплый DNS/HTTP-кэш WebView2 сохраняется между запусками (профиль не чистится).
- Предзагрузка top-сайтов из истории (prefetch DNS + preconnect) при простое UI.
- Видео: аппаратное декодирование включено (проверяется на M0 флагами и реальными
  дропами кадров); «экономия памяти»-режимы WebView2 выключены для активной вкладки.

## 2. Метрики (то, что проверяем, а не «ощущаем»)

\* Трактовка P-05 установлена автором 20.10.2026 (приёмка 5.3, вопрос
duopulse_035_p05_20261019): YouTube перевёл выдачу 1080p60 на AV1, на машинах
без аппаратного AV1-декода софт-декод даёт дропы и у нас, и у контроля —
ориентир «не хуже контрольного браузера на той же машине» (замер приёмки
19–20.10.2026: DuoPulse 16,5% против Chrome 16,7%). Исходный бюджет
«0 дропов/мин» остаётся целью при аппаратном декодировании играющего кодека.

Контроль для P-05/P-08 заменён по решению автора 21.10.2026 03:48 (вопрос
duopulse_047_control_20261021, CARDS/047): с 21.10.2026 YouTube-сервер не
attachит видеопоток свежим (без cookies) профилям Chrome И Edge на машине
автора (playerState 3, readyState 0 при playability OK; WebView2/DuoPulse в то
же время играет) — внешний Chrome/Edge-контроль невозможен, локально не
обходится (зонды — CARDS/047). Контроль = **DuoPulse с выключенным
блокировщиком** (settings.json `adblock.enabled=false`, стенды e2e/perf/p05.mjs
и p08.mjs): тот же движок и машина, разница только блокировщик. Плата —
потеря независимости движка (регрессии самого WebView2 контроль не поймает);
критерий «не хуже Chrome/Edge» сохраняется как справочный при возвращении
YouTube выдачи свежим Chrome-профилям (порог недоступности контроля снят:
отказ контроля теперь равен отказу прогона).

P-08 и SSAI-реклама (карточки 044/050, 22.10.2026): YouTube attachит преролл
серверным решением (USDAI/SABR) — клиентские скриптлеты его не подавляют:
любое вырезание `adSlots` из player-ответа ломает SABR-хендшейк (старт
16–20 с), поэтому compat-список DuoPulse нейтрализует adSlots-правила uBO
(adblock/compat.txt): старт видео как у контроля, SSAI-преролл играет
(клиентская реклама — playerAds/adPlacements — по-прежнему срезана).
Карточка 050 построила слой перезаписи сетевых ответов ($replace в
WebResourceRequested: самофетч через локальный роутер + замены в теле +
подмена ответа, adblock/replace.rs) — живые xhr-правила uBO применяются
(replacedRules/replacedTotal в adblock.status), но преролл на жёсткой
навигации это не убирает: SSAI-решение зашито серверно в SABR-манифест,
XHR-/player до первого кадра не зовётся, а переименование `"adSlots"`
в документе (проверено DUOPULSE_REPLACE_DEBUG) преролл не отменяет.
Инъекция живых trusted-replace-xhr-response uBO (per-list-доверие,
PermissionMask) подавляла преролл в 2/3 свежих сессий и формально закрывала
P-07 (19% ≤ 60%), но оплачевала ~8% к старту (P-08) — по умолчанию выключена,
выбор стороны трейд-оффа за автором (вопрос 050, Aila).

P-08 и стохастика SSAI (карточка duopulse-055, 24.10.2026): преролл
attach'ится серверным решением стохастично от сессии/профиля (утро 24.10:
сторона блокировщика — преролл в 5/5 прогонов, контроль — 1/5), поэтому
сравнение «медиана всех прогонов ≤ медиана контроля» неустойчиво: вердикт
меняла лотерея рекламы, а не качество продукта. С 24.10.2026 стенд
e2e/perf/p08.mjs стратифицирует прогоны по состоянию рекламы (adSeen):
вердикт — по паре ячеек РАВНОГО состояния (реклама-vs-реклама /
без-рекламы-vs-без-рекламы) при ≥2 прогонов в ячейке у обеих сторон;
недостающие ячейки добираются добавочными запусками (до 4 раундов — каждый
запуск новый тираж лотереи); пары нет — «вердикт не определён» (exit 3),
это не FAIL продукта. При наличии обеих пар решает пара «без рекламы»
(чистое сравнение движок+блокировщик), пара «с прероллом» репортится
справочно — правило утверждено автором 24.10.2026 12:12 (вопрос
duopulse_055_metric_20261024, выбор 1: «решает пара „без рекламы",
„с прероллом" справочно — чистое сравнение движок+блокировщик»). Число прогона = запуск → первый кадр ВОСПРОИЗВЕДЕНИЯ: при преролле
это первый кадр рекламы (стартовый путь рекламы входит в метрику, полная
длительность ролика — нет: она лотерея YouTube, не качество продукта).

Асимметрия стоимости преролла (утро 24.10: +1,5 с у блокировщика против
+0,4 с у контроля) объяснена трассировкой e2e/perf/p08-trace.mjs (CDP
Network + DOM-таймлайн до первого кадра, обе стороны): DNS+TLS к новым
хостам через SOCKS5-роутер НЕ причина (connect 21–143 мс, TLS 11–49 мс,
DNS на стороне прокси; суммарная стоимость новых хостов сопоставима —
блокировщик 175–343 мс, контроль 166–368 мс). Реальная стоимость — путь
запуска серверного рекламного ПОДа: несколько креативов с разными
медиа-id открываются последовательно (поды 29 и 69 с), иногда поверх уже
начатого контент-проба, поэтому прибавка к первому кадру разбросана от ~0
до ~1,5 с по запускам и не константа между сессиями: день 24.10
блокировщик-с-рекламой 2661–2836 мс против контроля-без-рекламы
2538–2704 мс — разница медиан 4% (утром было 49%). История равных
состояний: 22.10 обе стороны с прероллом 4311 ≤ 4700 PASS; 24.10 прогрев
DuoPulse-без-рекламы 2370 мс < контроль ~2585 мс. Базлайн методики 055
(24.10.2026, релизная сборка, три видео + трассировка, между прогонами
паузы ≥30 мин под лимит загрузок YouTube): dQw4w9WgXcQ (~12:00) — пары
равных состояний нет (блокировщик реклама 7/7 медиана 2706 мс, контроль
без 7/7 медиана 2600 мс, вердикт не определён, exit 3); aqz-KE-bpKQ 60fps
(~12:45) — пара «без рекламы» FAIL, 4096 мс [3648–4217] против 2546 мс
[2536–2624]; jNQXAC9IVRw (~13:20) — пара «без рекламы» FAIL, 3665 мс
[3596–3767] против 2455 мс [2401–2578]; трассировка того же jNQXAC9IVRw
(~13:45, e2e/perf/p08-trace.mjs) — ПАРИТЕТ: DuoPulse 2476 мс против
контроля 2546 мс, сетевой путь идентичен (те же хосты, одна медиа-проба,
DNS+connect 0–90 мс). Вывод базлайна: у стороны блокировщика есть
плавающая во времени деградация старта (от паритета до +1,2–1,5 с) при
стабильном контроле (~2,4–2,6 с на всех видео) — не функция видео и не
состояния рекламы; расследование — карточка 056 (итог ниже).

P-08 и themeRefresh-перезагрузка (карточка duopulse-056, решение автора
duopulse_056_trigger_20261024 вариант 1, 24–25.10.2026): механизм
плавающей деградации найден трассировкой — в «медленных» окнах YouTube
после успешного первого media-запроса (~1350 мс, паритет с контролем)
делает 401-навигацию accounts.google.com/ServiceLogin (пассивный логин) и
ПОЛНОСТЬЮ перезагружает watch-страницу (Document «…&themeRefresh=1») —
старт идёт заново, +1,2 с к первому кадру. Фильтр-листы исключены раньше
(быстрое окно на байт-идентичных замороженных списках медленного);
бисекция 25.10 (живое окно, ступени по 1 запуску, маркер окна — сам
themeRefresh): (1) compat-список без нашего активного json-prune
adPlacements/playerAds (исключения #@#+js сохранены) — перезагрузка 2/2;
(2) без мутаций рекламных полей вообще (easylist + ublock-ads минус 5
yt-правил set/json-prune, карточка 044) — перезагрузка есть; (3)
youtube.com полностью в site_exceptions (ни сети, ни косметики) — есть;
(4) блокировщик выключен целиком (конфигурация контроля) — перезагрузка
есть (3 конфигурации подряд в пределах 70 с). Итог: перезагрузку
инициирует сам YouTube — recovery-путь анонимной свежей сессии, вероятность
которого плавает по времени (сутки ранее коррелировала со стороной
блокировщика, утром 25.10 — бьёт и контроль); DuoPulse не причина и
предотвратить это на своей стороне не может. Поэтому с 25.10.2026 стенд
e2e/perf/p08.mjs помечает themeRefresh-прогоны (маркеры ServiceLogin /
themeRefresh=1 по Network-событиям цели и URL из /json) и пара вердикта
ищется сначала без них; если пара равного состояния рекламы собирается
только из themeRefresh-прогонов — вердикт «НЕ ОПРЕДЕЛЁН (окно
themeRefresh)», exit 3 — как лотерея SSAI, это не FAIL продукта.
Трассировка e2e/perf/p08-trace.mjs репортит маркеры по каждому прогону
(моменты ServiceLogin/themeRefresh в мс, поля в дампе; DUOPULSE_P08_SIDES
позволяет гонять одну сторону — экономия лимита загрузок YouTube).

Устойчивость p08 (карточка duopulse-052, 24.10.2026): транзитный сетевой сбой
на пути через SOCKS5-роутер (резолв «os error 11001») роняет перезагрузку
страницы YouTube (themeRefresh/пассивный логин) — вкладка честно уходит на
duopulse://error (карточка 048), youtube-цели в CDP нет. Такой прогон —
инфра-сбой запуска, а не медленный старт: p08 перезапускает его (до 3
повторов, каждый логируется); прогон с живой youtube-целью, но без кадра —
честный отказ метрики, не маскируется. Стенд также отказывается работать с
exe в dev-режиме (cargo build --release без tauri-CLI грузит UI с vite —
ловушка e2e/perf/run.mjs): замеры только с релиза npx tauri build.

Метрики снимает встроенная страница «Диагностика» (duopulse://diagnostics,
задача 2.5: живой срез сеанса + история последних 10 прогонов в SQLite,
график с бюджетами) и скрипты эталонного прогона (e2e/perf — одинаковый набор
URL/видео, 3 прогона, медиана) — чтобы сравнение было честным.

## 3. Бюджеты (защита от деградации)

- Бандл UI-хрома ≤ 300 КБ gzip; инжектируемый content-скрипт ≤ 80 КБ gzip.
- Вкладка «Диагностика» хранит последние 10 прогонов — регрессия видна на графике.
- Правило ревью: изменение, ухудшившее любую метрику > 10%, не мержится без
  явного решения «почему это ок».

## 4. Чего сознательно не делаем ради скорости

- Не проксируем весь трафик через «ускорители»/VPN-сервисы (приватность и честность).
- Не ломаем сайты агрессивной фильтрацией: приоритет — корректная работа; к спискам
  по умолчанию добавляем только проверенные.
- Не подменяем видео-разрешение/кодеки хаками плеера (риск банов и артефактов);
  ускоряем всё **вокруг** видео, а не сам плеер.
